# CLAUDE.md

## What Granit is

Granit is a minimal desktop note-taking app. It opens a local directory (a "cave") of markdown notes and provides a rendered reader, an explorer sidebar, an integrated streaming AI agent, slide presentations, and encrypted backups to a self-hosted server. Built for personal use — no plugins, no sync, no speculative abstractions.

## Workspace layout

A Cargo workspace with seven crates plus a JS build step. The frontend is being ported from Tauri + Leptos to GPUI (Bears epic `zem`); until the cutover both apps live side by side.

- `granit-ui` (root crate, `src/`) — Leptos 0.8 CSR frontend, compiled to WASM. Thin IPC view layer.
- `granit-core/` — host-agnostic backend logic with **no Tauri dependency** (keep it that way: `cargo tree -p granit-core -i tauri` must find nothing): `cave/`, `markdown/`, `agent/`, `backup/`, the shared `CoreState` (`state.rs`), the open-cave flow and RAG index build (`open.rs`), and the `granit://` URL builders (`urls.rs`). **Single source of truth** for state, file I/O, markdown rendering, cave operations, backups, and agent behavior. The GPUI app links it directly.
- `granit-app/` — the native GPUI app replacing `granit` + `granit-ui`: `gpui-pre` 0.3.12 (aliased as `gpui`) with GPUI Kit 0.10 and `zorite-editor` 0.11, one `gpui-pre` in the tree. Binary `granit-app` until the cutover (the Tauri package owns `granit`); product name `Granit`, bundle id `se.lhelge.granit`. See [GPUI app](#gpui-app-granit-app).
- `granit` (`src-tauri/`) — Tauri 2 shell around `granit-core`: IPC commands (`commands/`), events, plugins (store, dialog, opener, clipboard, log, updater), the presentation window, and the `granit://` request handler (`scheme.rs`). `lib.rs` re-imports the core modules at the crate root, so `crate::cave::…` paths still work there.
- `granit-types/` — shared types (config, document, agent, IPC payloads) used by both frontend and backend.
- `granit-api/` — wire types of the backup API, shared by the desktop client and the server.
- `granit-server` (`backend/`) — self-hosted backup server: axum, Postgres via sqlx (committed `.sqlx/` offline data, reversible migrations), S3-compatible storage (RustFS), Caddy. See [backend/README.md](backend/README.md).
- `js/editor.ts` / `js/mermaid.ts` — CodeMirror 6 and Mermaid, bundled by esbuild to `build/codemirror.js` / `build/mermaid.js` (`window.GranitEditor` / `window.GranitMermaid`). The Mermaid bundle is also served to the presentation window at `granit://asset/mermaid.js`.

## Build, test, run

```sh
npm ci                               # install JS deps (first time)
npm run build                        # Tailwind CSS + CodeMirror/Mermaid bundles into build/
cd src-tauri && cargo tauri dev      # run the full app (launches Trunk + Tauri)
trunk serve                          # frontend only, port 1420
cargo run -p granit-app -- <cave>    # run the GPUI app on a cave (not remembered as the last-open cave)

cargo fmt --all
cargo clippy -p granit -p granit-core -p granit-app --all-targets -- -D warnings  # backend + core + GPUI app
cargo clippy -p granit-ui --target wasm32-unknown-unknown -- -D warnings  # frontend
SQLX_OFFLINE=true cargo clippy -p granit-server -p granit-api --all-targets -- -D warnings

cargo test -p granit-core            # core tests: cave, markdown, agent, backup (cargo test -p granit-core <name> for one)
cargo test -p granit                 # Tauri shell tests: commands, scheme
cargo test -p granit-app             # GPUI app: headless gpui::test windows, no display needed
cargo test -p granit-types
cargo test -p granit-api
cargo test -p granit-server          # needs DATABASE_URL to a Postgres (backend/README.md)
wasm-pack test --headless --chrome   # frontend WASM tests (CI uses --firefox)

cd backend && cargo sqlx prepare -- --all-targets   # after changing any sqlx query
```

The frontend is a `wasm32-unknown-unknown` crate, so a plain `cargo clippy --workspace` fails on it. On Linux, `granit-app` needs the GPUI system libraries (xkbcommon, Wayland, Vulkan, fontconfig; the list is in CI's apt step) and a Vulkan driver to run. CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) and the git hooks run the commands above. Trunk does not produce `build/`, so `npm run build` must run before the frontend loads; use `npm run watch:css` / `npm run watch:js` while iterating. Tailwind scans `src/**/*.rs`, so new utility classes need a CSS rebuild.

Activate the version-controlled hooks once per clone with `git config core.hooksPath .githooks`: `pre-commit` checks formatting, `pre-push` runs the clippy and test commands (`GRANIT_WASM_TEST_BROWSER=firefox` to match CI).

## Architecture: backend-owned state

The backend is authoritative. The frontend holds reactive copies in `AppCtx` ([src/app/context.rs](src/app/context.rs)) but never owns logic. **If the frontend needs derived data, add a backend command rather than duplicating logic in WASM.**

- **`CoreState`** ([granit-core/src/state.rs](granit-core/src/state.rs)) is the host-agnostic state: `AppConfig`, the open `Cave` (`SharedCave = Arc<Mutex<Option<Cave>>>`, which also holds the active note), the lazily-built `Agent` and its generation counter, and the RAG `CaveVectorIndex` — each behind its own mutex — plus the backup `OperationGuard` (`backup_guard`), with the helpers `with_cave`, `ensure_agent` and `reset_agent`.
- **`AppState`** ([src-tauri/src/commands/state.rs](src-tauri/src/commands/state.rs)) is the `tauri::manage`d singleton: it wraps a `CoreState` (reached through `Deref`) and adds the Tauri-only parts, the shown presentation and the IPC config response. Event emitting stays in the command handlers; core code returns values instead.
- **IPC** is one `#[tauri::command]` per operation, all registered in `tauri::generate_handler!` in [src-tauri/src/lib.rs](src-tauri/src/lib.rs). Handlers are thin and delegate into `granit-core`'s `cave/`, `agent/`, `backup/`, or `markdown/`. The frontend calls them through the typed wrappers in [src/app/ipc.rs](src/app/ipc.rs).
- **Cave mutations** (including agent tool calls) emit `cave:notes-changed`; the listener in [src/app/mod.rs](src/app/mod.rs) refreshes notes/folders/active note. The active note slug is pushed back with `set_active_note` so agent tools can see it.
- **Errors** use `thiserror`, one enum per module (`CaveError`, `AgentError`, `BackupError`, …). Do **not** use `anyhow`.
- **Updates**: [src-tauri/src/commands/updater.rs](src-tauri/src/commands/updater.rs) checks GitHub releases on startup (not in debug builds) and keeps pending release notes in the store.

## Cave model

- A cave is any user-selected directory of markdown notes plus a `.granit/` directory: `config.yml`, `templates/`, `presentations/`, `agent/`, and the caches `embeddings.bin` and `backup.key`.
- **Filenames are globally unique across the whole cave**; a duplicate refuses to open the cave (`CaveError::DuplicateSlug`). The filename stem is the note's identity, slug, and displayed title; frontmatter does **not** override it. Slug matching is case-insensitive.
- Wiki-links `[[note]]` / `[[note|label]]` resolve by filename across the cave, not by relative path. Broken links are styled separately. Renaming a note rewrites the links to it.
- **Heading anchors**: `# Volvo {#volvo}` makes a link target in the same namespace as note slugs (`[[Volvo]]` resolves to `note#volvo`). Plain headings are not targets; a collision with a slug or another anchor refuses to open the cave (`CaveError::DuplicateAnchor`). `Cave::resolve_link` is the resolver passed to markdown rendering.
- `Cave` keeps in-memory indexes (notes, backlinks, anchors, templates, skills, tasks, presentations) populated lazily by `ensure_scanned()`. Use `CoreState::with_cave` / `with_shared_cave`, which lock, ensure-scan, then run a closure. Anything a mutation changes must be kept in sync in these indexes.
- **Opening a cave** is `granit_core::open`: `prepare_cave` (open, write a default config, load it, seed `system.md` with the legacy-prompt migration, seed presentation templates), then `CoreState::install_cave`, then `sync_vector_index`. Both hosts call it; the Tauri app also closes the presentation window and persists the path in between.
- Config is **cave-local** in `.granit/config.yml`. The last-open cave path lives separately: in `tauri-plugin-store` for the Tauri app, in `<config dir>/se.lhelge.granit/last-cave.json` for the GPUI app. `active_cave` is runtime-only in IPC responses and is **never** serialized into cave YAML. New config fields need serde defaults so existing caves still load. A new cave's `theme` is `system` (follow the OS, in both apps).
- Hidden directories and `.granit/` are excluded from note scans. Templates in `.granit/templates/` have their own flat slug namespace.
- **Presentation templates** are CSS files in the flat `.granit/presentations/` ([cave/presentations.rs](granit-core/src/cave/presentations.rs)); other files there are shared assets. Defaults are seeded in the open-cave flow when the directory is missing, never inside `ensure_scanned`. A note binds to one with the `presentation` frontmatter field.
- **`granit://` scheme** (served by [src-tauri/src/scheme.rs](src-tauri/src/scheme.rs), URLs built by [granit-core/src/urls.rs](granit-core/src/urls.rs)): `cave/<path>` (files under the cave root, e.g. note images) and `presentation/<path>` (template files, or the rendered page for a bare note slug). Paths are canonicalized and scoped to their root.

## Markdown

Rendered in the backend with `pulldown-cmark` ([granit-core/src/markdown/](granit-core/src/markdown/)). Frontmatter (`tags`, `created_at`/`modified_at`, `icon`, `favorite`, `presentation`) is parsed separately and never shown in the editor; the note header edits it. `read_note` returns the body (the file minus its frontmatter block, byte for byte) and `save_note`/`update_note` re-attach the existing block via `Markdown::rebuild`, which never re-serializes it: an unchanged save writes nothing, and a change splices only the touched owned keys (`tags`, `icon`, `favorite`, `presentation`, plus `modified_at`, stamped only when the body or an owned field changed) while unknown keys, order, comments, quoting and CRLF survive and `created_at` is never touched. What counts as frontmatter is decided in `locate_frontmatter` ([markdown/frontmatter.rs](granit-core/src/markdown/frontmatter.rs)): a leading `---` … `---`/`...` block that is blank, a YAML mapping, or invalid YAML whose first line looks like `key:` (kept verbatim and never stamped); anything else is body, and only the first block of a file is considered, so a body's own leading `---` block is never stripped. Raw HTML is sanitized before reaching the webview. Task-list checkboxes are interactive in the reader and disabled in agent-rendered markdown. Fenced `mermaid` blocks become diagrams only in the reader and on slides. Relative image sources are rewritten to the `granit://` cave route (`Markdown::with_image_base`).

**Presentations** ([markdown/presentation.rs](granit-core/src/markdown/presentation.rs), window in [commands/presentation.rs](src-tauri/src/commands/presentation.rs)): the body splits into slides on thematic breaks and renders as a standalone page in a single `presentation` window, reloaded on note/template save and closed on rename/delete/cave switch. The slide DOM and CSS custom-property contract is public — documented in [docs/content/wiki/presentations.md](docs/content/wiki/presentations.md) — and templates rely on it, so change it only deliberately and update that page.

## AI agent

All agent logic is backend-side ([granit-core/src/agent/](granit-core/src/agent/)), built on `rig-core` + `rig-agent`.

- **Providers**: Ollama, Anthropic, Mistral, and any OpenAI-compatible endpoint. Add one with match arms in `Agent::from_config` and `list_models` and a `ProviderConfig` variant.
- The `Agent` is built lazily by `CoreState::ensure_agent` and torn down (`reset_agent`, bumping the generation counter) whenever config, provider, model, or mode changes.
- **Tools** ([agent/tools/](granit-core/src/agent/tools/), catalogue in `mod.rs`) cover notes, folders, daily notes, todos, tags, templates (list only), text and semantic search, skills and agent docs, web fetch, and web search. `build_toolset` drops `disabled_tools`, `semantic_search` without a vector index, and `web_search` without a Brave key.
- **Modes** (`AgentMode`): `Ask` gets the read-only tools (everything outside `MUTATING_TOOLS`) plus injected RAG context; `Agent` gets all tools and no RAG injection.
- **Agent documents** live in `.granit/agent/` ([cave/agent_docs.rs](granit-core/src/cave/agent_docs.rs)): `system.md` is a Tera template rendered with `PromptContext` ([agent/prompt.rs](granit-core/src/agent/prompt.rs)), seeded from `DEFAULT_SYSTEM_PROMPT_TEMPLATE` when missing; `skills/<name>/SKILL.md` (Agent Skills format) are listed in the prompt and loaded with `use_skill`; `tasks/<name>.md` are user-invoked `/task` prompts.
- **RAG** ([agent/vectordb.rs](granit-core/src/agent/vectordb.rs)): `CaveVectorIndex` embeds notes with local CPU `fastembed` and caches them in `.granit/embeddings.bin` (`rkyv`). It must be built inside a tokio runtime, whose handle it keeps for its debounced updates. It is rebuilt in a background task (`granit_core::open::build_vector_index`, given the model directories and a tokio handle by the host) on cave open or RAG config change ([commands/config.rs](src-tauri/src/commands/config.rs)) and updated incrementally on UI note create/save/rename/delete ([commands/cave.rs](src-tauri/src/commands/cave.rs)).
- Streaming: `Agent::stream_with_history` returns an `AgentStream` of `AgentStreamItem`s (text / tool call / tool result / done).

## Backups

Client side in [granit-core/src/backup/](granit-core/src/backup/), settings in `AppConfig.backup` (backend URL and API key, saved in the cave's `config.yml`). A cave is archived (tar + zstd, `.git` excluded), encrypted locally with a key derived from a passphrase (Argon2id; the key is cached in `.granit/backup.key`, the passphrase never stored or logged), and uploaded through presigned URLs from `granit-server`. Restore goes to a new folder or replaces the cave in place (the old one is kept as `<cave>.pre-restore-*`); a disaster restore works with no cave open, with credentials given for the one request and never saved.

The flows both hosts run are in [backup/run.rs](granit-core/src/backup/run.rs): `backup_now`, `restore_backup` (a `RestoreRequest`: snapshot id, `RestoreTarget`, optional passphrase, optional credentials), `list_backups`, `delete_backup`, `set_cave_passphrase` and `cave_has_key`. A host first takes an `OperationTicket` from `CoreState::backup_guard()` (the one `OperationGuard`, which keeps backups and restores from overlapping) and passes a progress callback (`Fn(BackupStage)` / `Fn(RestoreStage)`). The flows talk to the backend through the `BackupApi` trait (`BackupApiClient`, an in-memory fake in the tests) and run blocking work with `spawn_blocking`, so they need a tokio runtime. An in-place restore closes the cave and resets the agent before swapping folders, but only if the open cave is still the one it was asked for (else `BackupError::CaveChanged`, nothing touched); `restore_backup` never opens a cave itself: it returns `Restored { cave, pre_restore }` for the host to open, or a `RestoreFailure` whose `reopen` names the original cave when a failed swap left it closed. The Tauri commands ([commands/backup.rs](src-tauri/src/commands/backup.rs)) turn the callbacks into `backup:*` / `restore:*` events and open the result with `open_cave_at`; the GPUI app goes through `backup_ops` (below). The server's API must change only additively, and merged migrations are never edited.

## GPUI app (`granit-app`)

`granit-app [<cave>]` opens the cave given on the command line (never remembered, so testing never touches the live cave pointer), else the last-open cave, else the folder picker (GPUI's `cx.prompt_for_paths`). Modules in [granit-app/src/](granit-app/src/):

- **`host.rs`**: the `Host` GPUI global holding `Arc<CoreState>` (`Host::core(cx)`), the last-cave store, the embedding-model dirs and whether the chat lists models (`HostOptions`; `HostOptions::default()` in tests persists nothing, builds no RAG index and never asks a provider for its models, so no test reaches the default config's local Ollama).
- **`cave_ops.rs`**: the UI's cave operations (open, list, read, create/rename/move/delete notes and folders, `create_note(folder, template)` (empty, or rendered from a note template through the core like the Tauri `create_note`), note templates (`list_templates`, `templates_for_new_notes` (all but the daily-note template), `read_template`, `create_template`, `save_template` (keeps the frontmatter, emits nothing), `rename_template`, `delete_template`), the agent's skills and tasks by `AgentDocKind` (`list_agent_docs`, `read_agent_doc`, `create_agent_doc` (`untitled-skill` / `untitled-task`, seeded by the core), `save_agent_doc` (body only, frontmatter kept byte for byte, emits nothing), `set_agent_doc_description` (splices only `description`), `rename_agent_doc` (a skill's folder moves and its `name` key follows), `delete_agent_doc`; over the core's `save_skill`/`save_task`, `set_*_description` and `rename_skill`/`rename_task` in [cave/agent_docs.rs](granit-core/src/cave/agent_docs.rs); a skill change that writes resets the agent (`reset_agent`, its history goes) as the Tauri skill commands do, but emits no `ConfigEvent`, so the visible chat stays and a running reply is just not recorded; task changes reset nothing), the note header (`note_header` / `template_header` (the core's `DocumentHeader`), `edit_note_header` / `edit_template_header` (one `HeaderEdit` to one frontmatter key, body kept as on disk; `NotesChanged` / `TemplatesChanged`)), `move_notes` / `delete_notes` (a multi-selection, one `NotesChanged` / `NotesRemoved` for all; a failing note does not stop the others), `list_favorites`, `note_count` (the sidebar footer's), set the active note, `open_daily_note(Option<date>)` (today for `None`; creates the day in `daily_note_folder` from `daily_note_template_slug` like the Tauri command, emitting `NotesChanged` only when it created one), `daily_note_slugs`, `toggle_todo`). Each runs on the core, keeps the RAG index current like the Tauri commands, and emits a `CaveEvent`. Synchronous on the foreground except opening, which prepares the cave on the background executor.
- **`events.rs`**: `CaveEvents`, the app-wide emitter of `CaveEvent` (`Opened`, `NotesChanged`, `NoteRenamed`, `NotesRemoved`, and for note templates `TemplatesChanged` (created, or icon/tags changed), `TemplateRenamed`, `TemplateRemoved`, and for skills and tasks `AgentDocsChanged` (created, or description changed), `AgentDocRenamed { kind, from, to }`, `AgentDocRemoved { kind, name }`; the chat re-lists its `/task`s on every event). Views `cx.subscribe(&CaveEvents::entity(cx), …)` and refresh; code that changes the cave outside `cave_ops` (agent tools) calls `CaveEvents::emit(CaveEvent::NotesChanged, cx)` from the foreground.
- **`config_ops.rs`**: the UI's config writes. `config_ops::update_config(cx, |config| …)` goes through `CoreState::update_config` ([granit-core/src/config.rs](granit-core/src/config.rs): an unchanged config writes nothing; otherwise `.granit/config.yml` is saved at once, never with `active_cave`, even when the agent config does not validate, and the agent is reset only when its config changed), rebuilds or drops the RAG index per `rag_index_action` (shared with the Tauri `save_config`), and emits a `ConfigEvent { agent, theme, fonts }` on `ConfigEvents`: the workspace re-themes, the note view and chat redraw with the new fonts, and the chat stops its reply, clears and re-lists models when the agent was reset. `config_ops::edit_config` is the deferred variant for text and number fields: it changes the in-memory config at once and commits (`CoreState::commit_config` against the config before the first edit) after a 500 ms typing pause (`COMMIT_DELAY`), on Enter or blur, when the settings close, before another cave opens, or before any `update_config` (`flush_config`; edits of a cave no longer open are dropped). A typed word is one save and at most one agent reset; a failed deferred save emits `ConfigSaveFailed` and keeps the edits pending against their baseline (shown, retried by the next flush, which then still resets the agent), and while they cannot be saved a cave switch is refused with the error in the sidebar, as for unsaved note edits (`Workspace::save_before_switch` flushes them even with the settings closed, through `flush_all`, and `before_install` again). `read_system_prompt` / `write_system_prompt` edit `.granit/agent/system.md` (the write resets the agent unless the text is unchanged; the settings textarea writes it on the same pause, blur or close; a prompt that cannot be written is kept in `config_ops`, outliving the view, and `flush_system_prompt` / `flush_all` retry it, so it too refuses a cave switch). `has_unsaved` tells whether either waits; the settings keep a failure shown until nothing does. `agent_ops` (the chat's provider/model/mode pickers) does not emit `ConfigEvents`.
- **`settings/`**: the settings view (`SettingsView`), shown in the main area instead of the note (sidebar gear button, `ToggleSettings`, `cmd-,` / `ctrl-,`; opening a note or another cave closes it), built on GPUI Kit's `Settings` component (page list with search; only the visible groups of a page render). Fields read the core's config when they render and write through `SettingsCtx::update` / `setter` (switches, pickers, buttons: saved at once) or `SettingsCtx::typed_setter` (text and number fields: `edit_config`); there is no Save button, and a failed write shows above the pages. Pages: Appearance (theme, note font = `reading_font`, chat font = `agent_font`), Notes (daily-note folder and template), Agent (max history/turns, the system prompt in a textarea, RAG, tools with the Brave key and limits), Providers (type, name, base URL, masked API key, add/remove; the selected provider and model stay in the chat panel), Backup (`settings/backup.rs`: backend URL and masked API key as typed config fields; passphrase set/change; Back up now with its stage; the snapshot list, listed when the settings open, after the credentials are committed (never per keystroke; `listed_with`), and after a backup or delete, with Restore… (complete snapshots: to a new folder via the folder picker, or over the current cave) and Delete. Its state lives in a `BackupPanel` entity the view owns. Replacing the cave and deleting ask first with a `window.prompt` dialog (`REPLACE_ANSWER` / `DELETE_ANSWER`); a restore whose cached key does not fit asks for the passphrase and retries, keeping the prompt with the error after a wrong one). A new section is a module with `page(&SettingsCtx, …) -> SettingPage` and a line in `SettingsView::pages`; `fields::text_field` (bound, optionally masked text input) and `fields::number_field` (instead of the Kit's `SettingField::number_input`) commit a typed edit on Enter and blur, which the Kit's fields cannot. Not offered: themes beyond Catppuccin light/dark, `markdown_font` (the Tauri app's raw-source editor font, kept in config for it), and presentation/Mermaid settings.
- **`backup_ops.rs`**: backups for the UI on top of `granit_core::backup::run`. The `BackupOps` global entity holds the running operation and its stage (`BackupOps::running`, `Running::label`) and emits `BackupEvent`s (`RestoreRequested`, `BackedUp`, `RestoreFailed { message, needs_passphrase }`). The flows run on tokio; their progress callback feeds a `tokio::sync::mpsc` channel drained by a GPUI task. Every operation commits typed settings edits first (`flush_config`), so it uses the credentials as shown. `backup_now`, `list(credentials)`, `delete`, `set_passphrase`, and `restore(request) -> Task<RestoreOutcome { open, error }>`; views ask for a restore with `request_restore`, and the workspace runs it (below), so it finishes and opens the cave even when the view is gone.
- **`disaster_restore.rs`**: `DisasterRestore`, the no-cave screen's "Restore from backup…" view in the main area (`Workspace::show_disaster_restore`): typed backend URL and masked API key (never saved), List snapshots, choose a complete one, an empty target folder (folder picker) and the passphrase (always needed: no cached key), then Restore; the restored cave opens and the view closes.
- **`runtime.rs`**: one process-wide multi-threaded tokio runtime (`runtime::handle()`, `runtime::spawn`). Await its `JoinHandle` inside `cx.spawn` to bring results back to the foreground; `runtime::spawn_abortable` aborts the tokio task when the awaiting GPUI task is dropped.
- **`workspace.rs`**: the root view (inside GPUI Kit's `Root`, opened by `open_main_window`): sidebar (cave name, open-cave, hide-sidebar, chat-toggle and settings buttons, then, with a cave open, the calendar above a GPUI Kit `TabBar` of `panels::SidebarTab`s switching between the explorer and the search, todos, tags, favorites, templates and agent files panels: `Workspace::show_tab`; `SEARCH_NOTES_KEY`, `cmd-shift-f` / `ctrl-shift-f`, jumps to the search box; below the panel a footer counts the cave's notes, "N notes" / "1 note", from `cave_ops::note_count` refreshed on every `CaveEvent`). The sidebar is shown or hidden with `ToggleSidebar` (`TOGGLE_SIDEBAR_KEY`, `cmd-shift-e` / `ctrl-shift-e`, since `cmd-b` is the editor's bold; `Workspace::toggle_sidebar`), saved in the cave's `sidebar.visible` (default shown) and reapplied on cave open; it is always shown with no cave open. While hidden a narrow rail left of the main area holds the show-sidebar and chat-toggle buttons (the Tauri app keeps both in its title bar); hiding it (by the toggle or by opening a cave whose sidebar is hidden) moves the focus from inside it (`sidebar_focus`) to the workspace, so the keys keep working, and tells the list panels they are hidden (`set_visible(false)`; showing it restores the selected tab's). The search key (and anything else that focuses into the sidebar, `Workspace::focus_search`) shows a hidden sidebar first and saves that. Its right edge is a `resize::PanelResize` handle (320–600 px, as in the Tauri app), saved to `sidebar.width` once, on mouse-up, with `config_ops::update_config`. Main area (the note, or the settings while open; opening a note from any panel closes them), and the chat panel on the right while shown (`ToggleChat`, `cmd-shift-a` / `ctrl-shift-a`; visibility saved in the cave's `agent_panel.visible`). It owns the open note: `Workspace::open_note` writes the open note's pending edits, then updates the core's active slug, the main view and the explorer selection (a note whose edits fail to save stays open); `Workspace::open_note_at(slug, Some(Reveal::{Anchor, Line, Offset}))` also puts the caret there, scrolled to the top (for search and todo matches); `Workspace::open_template(slug)` opens a note template in the same editor (flushing first, closing the settings; while it is open no note is active for the core, explorer or calendar), and `Workspace::open_agent_doc(kind, name)` a skill or task the same way. It follows `TemplateRenamed`/`TemplateRemoved` and `AgentDocRenamed`/`AgentDocRemoved` of the open document like notes, and `NoteRenamed` (pending edits go to the new name) and `NotesRemoved` (closed without saving). Before another cave opens it writes the editor's pending edits, and again right before the core swaps caves (`cave_ops::open_cave`'s `before_install` hook); if they cannot be written, the switch is refused and the error shown. A clicked chat link (`ChatEvent::OpenNote`) opens through `open_note_at`, with `Reveal::Anchor` for a heading anchor. The workspace tells the chat which note is open (`ChatPanel::set_active_note`, in `shown`) and answers `ChatEvent::AttachActiveNote` with `Workspace::attach_active_note`: `NoteView::attachment(window)` (slug, the editor's text with pending edits, the trimmed selected text) handed to `ChatPanel::attach`. Restores run in `Workspace::restore_backup` (on `BackupEvent::RestoreRequested`): an in-place restore first writes the settings' and the note's pending edits (refused if they cannot be written), then `backup_ops::restore`, then `open_cave` on the restored cave, or on the original one again after a failed swap, with the failure shown in the sidebar. `Workspace::open_cave` is refused (with the reason shown) while a restore runs. A cave that fails to open with the disaster restore shown reports the error in that view. With no cave open the main area offers "Open cave…" and "Restore from backup…".
- **`chat/`**: the agent chat panel (`ChatPanel`). The whole conversation is one Markdown document (`transcript.rs`) in a single GPUI Kit `TextView` (follows the bottom, selection across messages, no raw HTML, task checkboxes not clickable); user messages, tool calls and errors are top-level `> [!user]` / `[!tool]` / `[!error]` blockquotes drawn as Kit block surfaces. Replies stream from `Agent::stream_with_history` on tokio, one `AgentStream::next_item` per spawned step, with an entity update per item; tool results emit `CaveEvent::NotesChanged`, and the finished turn is recorded with `Agent::record_exchange` if the agent generation is unchanged. `wiki_links.rs` rewrites `[[t]]`/`[[t|label]]` to `[label](<wiki:t>)` on the stream, skipping code spans and fenced/indented code; `links.rs` resolves targets with `Cave::resolve_link` into a snapshot the view's `.link()` hook reads (broken links draw as plain text). Changing provider, model or mode (`agent_ops.rs`, which saves the cave config and resets the agent) cancels the running reply and clears the chat; "New conversation" clears the agent's history. `/task` completion and invocation (`tasks.rs`) as in the Tauri app. Models are listed only once the panel is shown. **Attached notes**, as in the Tauri app: above the input the open note is offered as a chip with a `+` (not attached by default); attaching freezes its text and the editor's selection at that moment (one attachment per slug, removed with its `×`), and every message sent goes through `build_agent_prompt(message, attached)` while the transcript shows only what was typed; attachments stay until removed or another cave opens; a template is never offered. **Width**: the panel's left edge is a `resize::PanelResize` handle (240–640 px); the width follows the drag and is saved to `agent_panel.width` once, on mouse-up, with `config_ops::update_config`.
- **`resize.rs`**: `PanelResize`, a side panel resized by dragging its edge, built on GPUI Kit's `resize_handle` (`HandleEdge::Leading` for a right-side panel, `Trailing` for a left one). The owning view keeps one, wraps the panel root with `attach(panel, state, resized, cx)` (follows `DragMoveEvent<EdgeDrag>` for its own id, ends on any mouse-up) and adds `handle()` as the root's last child; it draws `width(saved)` and saves in `resized`. The chat (leading edge) and the sidebar (trailing edge) use it.
- **`panels/`**: the sidebar panels beside the explorer, each emitting `PanelEvent::OpenNote { slug, reveal }` (the workspace opens it with `open_note_at`). `SearchPanel` (GPUI Kit searchable `List`; each keystroke reruns `Cave::search_lines` after `SEARCH_DELAY`, rows are notes with their matching body lines, opened at `Reveal::Line`), `TodosPanel` (`Cave::list_todos` grouped by note, done ones folded under "Completed"; a todo opens at its line via `Cave::todo_body_line`; its checkbox emits `PanelEvent::ToggleTodo`, which `Workspace::toggle_todo` handles by flushing the editor when that note is open, then `cave_ops::toggle_todo`, which re-finds the todo with `Cave::locate_todo` so moved lines toggle the right one; the editor then reloads the clean note), `TagsPanel` (`Cave::list_tags` with counts; a click lists one tag's notes below it), `FavoritesPanel` (the notes with `favorite: true`, `cave_ops::list_favorites`, with a count; a click opens one, the open note is highlighted; reread synchronously after cave events while shown, stale while hidden), `TemplatesPanel` (the note templates of `.granit/templates/` with their icons; a click emits `PanelEvent::OpenTemplate`; new (opens it and renames it inline), inline rename and delete buttons per row; a foldable "Template parameters" list of the Tera variables; refreshed synchronously on every cave event), `AgentFilesPanel` (`SidebarTab::Agent`, `agent_files.rs`: a Skills and a Tasks section with name and description per row, emitting `PanelEvent::OpenAgentDoc { kind, name }`; new, inline rename and delete like the templates panel; a foldable "Agent files help" with the tasks' Tera variables; the system prompt stays in the settings) and `CalendarPanel` (always shown above the tabs; month grid from `granit_core::calendar::Month`, ISO weeks Monday first; days with a note (`Cave::daily_note_slugs`) bold, today outlined, the open note filled; a click calls `cave_ops::open_daily_note`, and the daily-note button beside the month, `CalendarPanel::open_today`, does it for today). The list panels run their queries on the background executor and only while shown (`set_visible`): a cave change marks a hidden one stale, and it reruns when shown. Lists use GPUI Kit's `List`/`ListDelegate` with one row height (`ROW_HEIGHT`) and flat row enums.
- **`explorer/`**: the note tree on GPUI Kit's `Tree` (`tree_model.rs` builds it, `row.rs` renders rows with note icons and favorite stars, inline rename input, drag and drop). Emits `ExplorerEvent::OpenNote`. "New note from template" is a header dropdown (cave root) and a folder context-menu submenu ("New note here from template"), both listing `cave_ops::templates_for_new_notes`; `Explorer::new_note_from(folder, template)` creates, opens and starts renaming the note. A right-click on the empty space around the rows (the `explorer-tree` area; a row's own menu takes its right-clicks) opens the root menu of the Tauri app: New note, New note from template (submenu), New folder, all in the cave root (`Explorer::root_menu`). Notes multi-select as in the Tauri app (`Explorer::click_note` with a `ClickKind` from the click's modifiers, applied by the row's click handler before the tree's own): Ctrl- or Cmd-click toggles a note without opening it (the handler stops propagation), Shift-click selects the range from the last clicked note in visible tree order (`tree_model::visible_note_slugs`) and opens it, a plain click selects only it; a selection of one follows the open note. Dragging a note of a multi-selection drags all of it (`dragged_entries`, `move_entries` → `cave_ops::move_notes`), and the note context menu's "Delete N notes" deletes it (`notes_for`, `delete_notes`), without confirmation like a single delete. Folders are not selectable; Escape does not clear the selection (neither does the Tauri app's).
- **`note_view/`**: the main area, the open note in the `zorite-editor` live-preview editor (from the fork branch `LHelge/zorite-editor` `fix/stale-layout-input` through `[patch.crates-io]` in the workspace `Cargo.toml`, until a release carries the stale-layout fix). The editor never sees frontmatter: it loads `Cave::read_note(slug).content` and saves through `cave_ops::save_note`, which re-attaches it. It holds a document of a `DocKind`, `Note`, `Template`, `Skill` or `Task` (`DocRef { kind, slug }`; the slug namespaces are separate, so sessions and `SaveSnapshot`s carry the kind): `NoteView::open` opens notes, `open_doc` any; a skill or task loads its body without frontmatter (`Cave::read_skill`/`read_task`) and saves through `cave_ops::save_agent_doc`, its header shows a "Skill"/"Task" badge, the title (rename) and a description input (no icon, tags or dates) that writes on Enter, blur or any flush of the view (`NoteView::commit_description`), its images resolve from the skill's folder or the tasks folder; a task's wiki-links are treated like a template's (Tera placeholders, never broken), a skill's (never rendered with Tera) are marked broken like a note's, and a click on a broken link in either creates nothing; a template loads through `Cave::read_template` and saves through `cave_ops::save_template` (Tera syntax round-trips as written), its header shows a "Template" badge, its images resolve from `.granit/templates/`, its wiki-links are never marked broken and a click on a broken one creates nothing (they may be placeholders like `[[{{ yesterday }}]]`), while `[[` completion and links to existing notes work. `NoteView::slug` is the open *note's* slug only.
  - Each opened note gets a fresh `EditorState`, created once the window is free (`cx.defer`, before the next paint), so input queued behind a slow frame cannot hit a stale layout. One `CodeHighlighter` (GPUI Kit tree-sitter, one highlighter per language) and one `ImageCache` are shared by all editors. Styling comes from the theme (`style.rs`) and is re-applied whenever the `Theme` global changes; the editor font is `style::editor_font`, the config's `reading_font` (the live preview is also the reading view) resolved against the theme; code stays in the theme's monospace font.
  - **Save path** (`save.rs`): an edit starts a 2 s holdoff (`AUTOSAVE_DELAY`); the save key, a note switch, the editor losing focus, a cave switch, closing the window and quitting write at once. Every write goes through a `SaveSnapshot` of (slug, text) taken at that moment, never the live editor, and is refused once another cave is open. An unedited note (or one typed and reverted) is never written. A note that used CRLF throughout is written back with CRLF on every line (the editor inserts bare `\n`). On `NotesChanged` a clean note reloads if its body changed on disk; one with pending edits keeps them and the next save overwrites the change.
  - The editor's `set_text` splits a `$$` that shares a line with words onto its own lines (`normalize_loaded`), and does the same to the typed paragraph (`normalize_math_at`); `note_view::load_text` puts the loaded body back with `replace_range` (and the view refuses an undo from the loaded body, which would apply the split), and an always-firing empty `set_auto_replace` rule keeps the typing path off. Both are workarounds for zorite-editor behaviour (Bears `zem.vs`).
  - **Wiki-links** (`links.rs`, logic in `wiki_links.rs`): where links, code and `{#id}` headings are comes from granit-core's `Markdown::link_spans` (one pulldown-cmark pass with the renderer's options; `wiki_link_targets`, `anchor_ids` and `rename_wiki_links` use it too, so the editor agrees with the reader, backlinks and `list_broken_links`), cached per text in a `SpanCache` so an edit parses once (~2.5 ms release / ~12 ms debug for a 6,900-line note); only the `[[` query, the completion edit, the ranking and `LinkIndex` (built from `Cave::anchor_notes`) stay in the app. A click on `[[note]]`, `[[note|label]]` or an `{#id}` anchor resolves through `Cave::resolve_link` and asks the workspace to open it (`NoteViewEvent::OpenNote`); a broken target creates the note in the cave root, like the web app. Broken links get the editor's diagnostic underline. `[[` opens completion of slugs, anchors and broken targets (Up/Down/Enter/Tab/Escape, captured from the editor's actions), not inside fenced, indented or inline code or raw HTML blocks. Anchor reveals find ATX and setext headings. External `http(s)`/`mailto` links open in the browser.
  - **Header** (`header.rs`), fixed above the editor, as the Tauri note header has it: a "Template" badge for templates, the icon button (a GPUI Kit `Popover` with a search field over `granit_types::search_note_icons` and a grid of `NOTE_ICONS`, plus "Remove icon"), the favorite star (notes only), the title (a click turns it into an input; Enter or blur renames through `cave_ops::rename_note` / `rename_template`, Escape cancels; pending edits follow the rename), the save state, tag pills with remove buttons and an "Add tag…" input (Enter or a comma adds; trimmed, lowercased, no duplicates: `granit_core::cave::normalize_tag`), one line of created/modified dates, word count and reading time (`Markdown::stats`), and for notes a foldable "Backlinks (n)" section whose rows open the linking note (`NoteViewEvent::OpenNote`). What it shows is `Cave::note_header` / `template_header` of the file on disk, re-read on load, on every save and on every cave event. A header edit (`NoteView::edit_header(HeaderEdit)`) first writes the editor's pending edits (if that fails, nothing changes and the error shows in the header), then changes only its own key (plus `modified_at`) through `cave_ops::edit_note_header` / `edit_template_header`. Templates get the icon, tags, dates and word count, no star and no backlinks (their slugs are a namespace of their own).
  - **Find and replace** (`find.rs`): a bar above the editor (header search button or `FIND_KEY`; `find_in_source` / `set_search`), seeded with a one-line selection or else the last closed bar's query; Enter and Shift-Enter step, as do `FIND_NEXT_KEY` / `FIND_PREVIOUS_KEY` (which open the bar at the match after / before the caret when it is closed); the replace field's Enter or "Replace" replaces the current match, "All" every match as one undo step (`replace_all_edit`); Escape closes. **Alerts** (`alerts.rs`): `> [!` at a line start offers the five GitHub alert types in the `[[` popup (`CandidateKind::Alert`); accepting inserts `[!TYPE]` and a `> ` line. **Select next** (`SELECT_NEXT_KEY`, `commands::select_next`): selects the word at the caret, then moves the selection to the next occurrence (zorite-editor has one selection, so it moves rather than adds; set through `NoteView::select_range`, an input-handler workaround for the missing selection setter whose `Changed` echo is ignored). **Copy note** (header copy button, `NoteView::copy_as_html`): the body (pending edits included, no frontmatter) rendered with `Markdown::render_for_export` goes on the clipboard as HTML with the markdown as plain text, through [`clipboard.rs`](granit-app/src/clipboard.rs) (`arboard`, since GPUI's clipboard has no HTML flavour; falls back to plain text on GPUI's clipboard when that fails or, in tests, when no `RichClipboard` is installed). **Images** (`images.rs`): `![](src)` resolves against the note's directory (`granit_core::markdown::cave_image_path`, a leading `/` from the cave root, never outside it, following the note when it or its folder moves) and is decoded on the background executor.
  - **Shortcuts** (bound in the `NoteView` key context by `note_view::bind_keys`, which `workspace::bind_keys` calls): `SAVE_KEY` (`-s`), `FIND_KEY` (`-f`), `FIND_NEXT_KEY` (`-g`), `FIND_PREVIOUS_KEY` (`-shift-g`), `INSERT_LINK_KEY` (`-k`: wrap the selection as `[[…]]`, a URL as `[](…)`, or insert `[[]]`), `TOGGLE_TASK_KEY` (`-l`) and `SELECT_NEXT_KEY` (`-d`, bound in `NoteView > Editor` so it replaces zorite-editor's Duplicate on that key; Duplicate lines stays on `-shift-d`), each `cmd-` on macOS and `ctrl-` elsewhere; formatting (bold, italic, code, strike, highlight, undo, …) comes from `zorite_editor::bind_keys`.
- **`theme.rs`** / `themes.json`: Catppuccin Latte and Frappé; read colors with `cx.theme()`. Which one shows is the cave config's `ThemeChoice` (`AppConfig::theme_choice`: `system`, the default, follows the window appearance); `theme::sync` re-applies it on an appearance change, cave open or theme setting. The config keeps the Tauri app's free-form `theme` name: known DaisyUI/community dark themes read as Dark, light ones as Light, anything else as System, and reading never rewrites it; choosing writes `light`, `dark` or `system`, which the Tauri app also accepts (an unknown `data-theme` falls back to DaisyUI's `prefers-color-scheme` themes). `theme::resolve_font` maps the stored CSS generics (`sans-serif`, `monospace`, …) to the theme's fonts. **`assets.rs`**: GPUI Kit's icons plus the note-icon catalog (`note-icons/<Id>.svg`, built from `granit_types::NOTE_ICONS`) and a few `AppIcon`s.

The panels' queries are the core's: `Cave::search_lines` (search with 0-based body line numbers; `search_content` is built on it), `Cave::locate_todo` / `Cave::todo_body_line` ([cave/todos.rs](granit-core/src/cave/todos.rs)), `Cave::daily_note_slugs` ([cave/templates.rs](granit-core/src/cave/templates.rs)), the note header's `Cave::note_header` / `template_header` / `edit_note_header` / `edit_template_header` ([cave/header.rs](granit-core/src/cave/header.rs)) and the month grid in [granit-core/src/calendar.rs](granit-core/src/calendar.rs) (`Month`, `today_slug`).

Tests are `#[gpui::test]`s on GPUI's headless test platform ([granit-app/src/tests.rs](granit-app/src/tests.rs) has the `App` harness); render paths are exercised with `window.draw(cx)`.

## Frontend conventions

- Leptos signals + the `AppCtx` context (`expect_context::<AppCtx>()`) rather than threading props. IPC goes through the [src/app/ipc.rs](src/app/ipc.rs) wrappers.
- The editor autosaves after a 2 s holdoff; saves go through the snapshots in `editor/save_queue.rs`, never live signals, so a quick note switch cannot write to the wrong slug.
- Styling is Tailwind CSS 4 + DaisyUI 5 utility classes written directly in `view!` macros. Prefer DaisyUI component classes before hand-rolling.
- Icons use `leptos_icons` + `icondata_lu`. `Icon` has **no** `class` prop — put sizing/color/spacing/rotation on a wrapper element. Provider brand assets live in `ProviderIcon` ([src/app/components/icons.rs](src/app/components/icons.rs)).

## Conventions

- All code, comments, and docs in English.
- Build only what is needed now. No plugin system, sync layer, or speculative abstractions (deferred: file watching / external reload, live-preview editor, sync).
- A change to features, configuration, or behavior updates this file where it describes that part and the user docs in `docs/content/wiki/` (built with aphid; see the `aphid-content` skill) in the same change.
- **Release notes are generated from commit messages**, so each feature lands as one focused commit with a Conventional Commits subject in the user's terms. Don't commit after a first implementation pass — present the result, iterate on feedback, and commit only once the feature is agreed done. Follow-up tweaks in the same session are amended or squashed into the feature commit rather than added as `fix`/`refactor` commits (never amend commits that are already merged or that others may have pulled).
  - **Exception:** under the `implement-epic` skill the user has delegated review to the `task-reviewer` agent, so each Bears task lands as one commit once its review passes, without waiting for the user.
- The repo owner is strong on Rust backend work and less experienced with Leptos/Tailwind/DaisyUI — be more explicit and cautious for frontend changes.
- Before committing, run `cargo fmt` and the clippy and test commands above for the crates you touched.
